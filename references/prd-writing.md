# PRD 写作

依据用户提供的 [create-prd 原文](create-prd-source.md)。输出 `PRD-<product-name>.md`，默认用中文、短句和产品语言；已有文档尊重其结构与内容。

## 状态行与定稿

PRD 文首（标题下一行）写状态行：

> 状态：草稿 ｜ 待决策 ｜ 已审查通过（YYYY-MM-DD）

- **草稿**：内容补全中，不作为原型依据。
- **待决策**：正文完成，但决策记录仍有未决问题，等用户选择。
- **已审查通过**：用户明确确认后的定稿，只写一次日期。只有这个状态才进入原型绘制；validate 与生成的 HTML 都会呈现该状态。

定稿后任何需求性修改（功能、规则、文案、流程）先把状态改回「草稿」，修改完成、用户重新审查通过后再标回。仅修正错别字不改状态。「已审查通过」只能来自用户本次明确表达；用户口头表示通过时，可代为写入状态行并注明日期，不虚构。

## 决策记录（7.4 内）

未能确定的事项不擅自决定、不散落正文，集中写入 7.4「假设与待确认」下的决策记录，一条一个问题：

```markdown
### 决策记录
- **Q1（待决策）**：列表默认按什么排序？
  - 背景：影响列表页首个屏幕的默认呈现与验收口径。
  - 选项 A：创建时间倒序 —— 新内容优先，符合资料沉淀场景（AI 建议）。
  - 选项 B：最近更新倒序 —— 进行中工作优先，但新内容容易被淹没。
  - 用户决策：待选择
```

- 选项互斥、可执行，各附一行影响或代价；有依据时给出 AI 建议及理由，没有依据明说不建议。
- 问题按对流程的影响排序，一次提出全部待决项，不挤牙膏；不假设相似问题的答案一致。
- 用户回答后：把「用户决策」改为所选内容、日期并标「已决策」；同时把决策结果写回相关章节正文，消除正文对应的「待确认」。已决策记录保留不删除，作为变更追溯。
- 正文中的规则仍按已决策结果写实；决策记录只承载"待定 → 已定"的过程，不替代正文描述。

1. **摘要 / Summary**：2–3 句话说明产品或改动。
2. **联系人 / Contacts**：姓名、角色、备注。未提供人员时写「待确认」。
3. **背景 / Background**：用户问题、业务背景、为何现在做，区分输入事实和假设。
4. **目标 / Objective**：公司与用户获得的价值，如何衡量成功；用 SMART OKR 表达已知目标，未知基线、目标值和周期标待确认，不编数字。
5. **目标市场 / Market Segments**：按用户问题和要完成的任务划分，写约束，不按虚构人口属性划分。
6. **价值主张 / Value Propositions**：任务、收益、减少的痛点和差异化。没有竞争证据时不虚构研究结论。
7. **方案 / Solution**：7.1 用户体验与原型；7.2 核心功能；7.3 技术（仅相关时）；7.4 假设与待确认。状态、规则和验收放在第 7 章相应功能下。
8. **发布 / Release**：首版范围、后续范围及相对时间，不凭空给出精确日期或承诺排期。

第 7 章需要支撑原型时，建议为需求分配稳定编号。每条规则写清“是什么、何时出现、用户可做什么、结果是什么”。按真实使用顺序列流程分组、页面状态、触发方式、核心文案、操作目标、PRD 依据。加载 / 空 / 失败 / 恢复 / 权限等状态只纳入 PRD 明示范围；没有明确的相关规则列为待确认。

原型说明的写法继承 proto-gen 的旁注思路并扩展为完整面板：每屏用 `summary` 说清任务与进入条件、`layout` 说清布局分区职责、组件级 `note` 一条一个可感知元素（展示什么、如何操作、发生什么、数据与校验规则）、`logic` 写清条件展示与边界；不要把 CSS 类名、像素、技术事件写进产品文案。规范细则见 [wireframe-guide](wireframe-guide.md) 的「原型说明写法」。对既有产品的改动，额外记录观察到的原逻辑及本次修改点；线框仍保留理解完整流程所需的上下文。

用户提供资料时先读资料。需要研究的外部信息可按当前工具规则查询、引用；产品截图走查遵循 SKILL 的计划确认步骤。提供网址不等于可以跳过确认执行产品走查。
