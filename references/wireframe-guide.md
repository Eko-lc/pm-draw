# 线框图与原型方案说明规范

把《用户体验要素》（Jesse James Garrett）、《交互设计精髓》（Alan Cooper）、《俞军产品方法论》中的方法，落到本工具的流程 JSON、线框组件和截图标注上。本文件是绘制与评审依据，不替代 PRD。

## 方法论到机制的映射

| 方法论 | 核心观点 | 本工具对应机制 |
| --- | --- | --- |
| 用户体验要素 · 战略层 / 范围层 | 先明确产品目标与需求范围，再谈界面 | 八章 PRD；requirements 必须引用 PRD 原文，不擅自加功能 |
| 用户体验要素 · 结构层 | 交互设计与信息架构：用户走哪条路、每一步到哪去 | groups 按真实使用顺序排列；一屏 = 页面 + 状态；actions 的 to / outcome 显式声明去向 |
| 用户体验要素 · 框架层 | 界面设计、导航设计、信息设计三者合成线框：元素摆在哪、如何去下一屏、信息怎么分组分层 | 线框组件、heading 1–3 级层级、每屏「上一屏 / 第 n 屏 / 下一屏」导航、全局索引 |
| 用户体验要素 · 表现层 | 视觉表现放在最后，避免过早争论颜色样式 | 线框只用中性灰加低饱和功能色（见下文配色规范）；真实视觉以产品截图为准 |
| 交互设计精髓 · 目标导向 | 界面围绕用户要完成的任务组织，一屏一个清晰主操作 | 每屏 actions 最多一个 `role: primary`；其余为 secondary |
| 交互设计精髓 · 反馈与防错 | 操作后必有明确反馈；出错、空、加载等状态要显式设计，而不是默认异常 | action 必填 outcome（操作后发生什么）；空 / 失败 / 权限等状态是独立 screen；未知规则进 pending，不编造 |
| 俞军产品方法论 · 用户价值与场景 | 需求从「谁、在什么场景、要完成什么、得到什么结果」出发；每条决策可追溯依据 | requirement 的 text 写任务与结果；quote 绑定 PRD 原文；标注写「原逻辑—依据—修改点」 |

## 线框绘制规则

1. **一屏只画一个页面状态**，线框顶部状态条自动带出「页面名 · 当前状态」；同一页面的不同状态各占一屏。
2. **信息层级用结构表达，颜色只做辅助强调**：heading `level` 1 为页面主标题、2 为区块标题、3 为小节标题；分组用 section / columns；层级靠字重、框线和留白，颜色不参与区分普通层级。
3. **核心文案写实**：按钮用动宾短语（「新建资料」而非「确定」）；notice 写真实提示语；field 的标签与占位文案是最终文案的候选，不用 lorem ipsum；写不出的文案标「待确认」。
4. **按钮位置必须可见**：每个操作在原型里有对应 action 组件（校验器强制）；主操作每屏最多一个，放在用户视线路径的终点附近。
5. **图片只用占位块**，写明图片内容是什么，不贴真实图。
6. 线框不表达像素、动效，不为单个组件临时指定色值；这些属于实际产品或后续视觉稿。颜色语义统一由配色规范决定。

## 功能性配色规范（低保真）

纯黑白灰难以区分主次与状态，本工具改用「中性灰 + 低饱和功能色」：颜色只承担**功能区分、状态提示、层级强调**三种语义，不做视觉美化；不使用品牌色、渐变和高保真配色。一套方案共 **5 种颜色（含中性灰）**，新语义先复用已有颜色，不新增色相。

| 颜色 | 值（浅底） | 语义 | 允许出现在 |
| --- | --- | --- | --- |
| 中性灰 | `#f4f3f1` / `#ffffff` / `#2b2b2b` / `#c6c4bf` | 底色、文字、框线与占位 | 所有结构与图片占位块，不表达状态 |
| 雾蓝 | `#4d6a8a`（浅底 `#e9eef4`） | 主操作、当前导航、联动高亮、说明提示 | primary 按钮、主操作标签、notice 说明、标题强调线 |
| 灰绿 | `#4d7c5f`（浅底 `#e8f0ea`） | 正向状态 | 「已审查通过」「符合预期」 |
| 灰琥珀 | `#7d612a`（浅底 `#f4eedd`） | 注意状态 | 「草稿」「待确认」「已改动 · 待回归」「需要调整」 |
| 砖红 | `#b0524a`（浅底 `#f6eae8`） | 异常与截图标注 | 「严重问题」、保存失败提示、截图标注矩形 / 圆点 / 箭头 |

1. 颜色不承载唯一信息：每个状态必须同时有文字（如「待确认」「已改动 · 待回归」），去掉颜色后仍可读。
2. 线框内颜色只出现在按钮、状态徽章、notice 和待确认标记；普通文本、表格、字段和占位块保持中性灰。
3. 砖红同时服务异常状态与截图标注覆盖层，除此之外不得引入任何新颜色。

## 每屏方案说明五要素

每屏必须能让人不问人就读懂，构建产物自动呈现：

1. **页面名称**：screen 的 `page`，出现在屏标题与线框状态条。
2. **流程位置**：所在分组、「第几步 / 共几步」、底部「上一屏 / 第 n / N 屏 / 下一屏」导航；跨分组时导航与操作跳转链接到对应分组页面（`<group>.html#screen-<id>`）。
3. **当前状态**：`state` 要具体（如「无资料」「提交失败」），不用「页面 1」代替。
4. **可执行操作**：`actions` 的 label 即按钮文案；面板中按「操作 → 去向 + 结果」逐条列出。
5. **操作后进入哪个页面或状态**：`to` 填目标 screen id（生成可点击锚点）、`null`（流程终点 / 当前状态内操作）或「待确认」；线框按钮下方同步标注跳转目标；自动流转用 `transitions` 与人工操作区分。

## 原型说明写法

每屏右侧的「原型说明」面板是评审与开发的主要阅读区，目标是**不翻 PRD 也能看懂本屏的逻辑、布局与交互**。参考业界原型标注规范（布局说明区域含义、交互写触发条件与结果、逻辑写清边界，颗粒度到「能实现、能测试、能验收」），按以下结构写：

1. **页面说明 `summary`**：一句话说清本屏任务与进入条件——用户在这里完成什么、什么情况下看到这个状态。不复述页面名，不抄 PRD 编号。
2. **页面布局 `layout`**：按视觉顺序（通常从上到下）说明每个分区的职责，如「顶部：标题与全局操作」「中部：列表区，空数据时显示空状态」。说明区域含义即可；间距、颜色、字体等纯视觉细节交给实际产品或视觉稿，不写进原型。
3. **组件说明 `blocks[].note`**：一个可感知元素一条，回答四个问题——**展示什么**（内容来源、格式、默认值）、**如何操作**（触发条件，如点击 / 输入 / 悬停）、**发生什么**（反馈、校验、跳转）、**规则约束**（必填、长度、格式、权限）。写了 note 的组件在线框中自动编号，与说明列表一一对应、悬停联动高亮。自明的纯文本 / 装饰组件可不写；每条一个意思，写不出规则的标「待确认」而不是编造。
4. **逻辑规则 `logic`**：跨组件的条件与边界——什么条件显示什么、数据为空 / 接口失败 / 权限不足时页面怎样、排序与分页规则。写成可执行判断句（「若…则…」），让开发可以直接对照实现；未明确的规则不进 logic，进 `pending`。
5. **交互与状态流转**：沿用 `actions` / `transitions` 自动呈现，操作写清「能做什么、做完发生什么、到哪去」。
6. **PRD 依据**：requirements 原文折叠在面板底部「PRD 依据」中，只作可追溯来源，不再作为面板主内容；说明文字必须与 PRD 语义一致，不一致时先改 PRD 再改说明。

## 截图标注规则（方案叠加在真实截图上）

走查既有产品时，方案直接标注在原截图上，与低保真线框并排：

1. **红色编号矩形** `rect`：圈出要讨论的区域；**红色圆点** `pin`：标记精确控件或位置；**红色箭头** `arrow`：从矩形 / 圆点出发，指向相关联的区域（如「点击处 → 反馈出现处」「当前元素 → 期望位置」）。三者都是覆盖层，不修改原图。
2. 编号与右侧「原逻辑与修改点」列表一一对应；每条标注写清：**原逻辑**（只写实际观察到的，没观察到写「待确认」）、**PRD 依据**（requirement 编号）、**修改点**（相对设计原意要改什么）。悬停任一条目会同时高亮截图标识和对应线框组件。
3. 一屏标注聚焦关键差异，通常 1–5 条；整屏都是差异时说明整体重做，不堆满编号。
4. 标注红只用于截图标注与对应编号；线框内不出现标注红，线框颜色仅限配色规范中的功能语义，避免把「标注」误读为「设计」。

## 文案与交互说明写法

- 说明文字一条一个意思，短句；先结论后依据：「操作 → 去向」一行，「结果」一行。
- 交互说明回答三个问题：用户能做什么（label）、做了之后发生什么（outcome）、然后到哪去（to）。缺任何一个就是待确认。
- 反馈记录沿用「页面—状态—问题—建议」，原话保留，不改写不总结。
- 版面错落有致：分组标题、屏、面板小节三级标题递进；卡片之间留白；列表不嵌套超过两层。
